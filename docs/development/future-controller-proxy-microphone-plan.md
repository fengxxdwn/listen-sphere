# 后续路线：主控端代理麦克风与反向音频链路

## 状态

**暂缓，不进入下一开发阶段（2026-09-02）。**

普通 Android 应用只能把反向流播放到手机扬声器或耳机，无法可靠注入系统电话、
微信、QQ 等第三方通话的麦克风上行；通话期间还可能被系统或厂商音频策略静音。
因此本计划不作为 R4 实施，保留为技术研究资料。只有在产品明确接受“仅反向监听”、
改为自有通话链路，或取得 OEM/系统级能力时再重新评估。

## 目标

在 Sender 向 Controller 传输应用声音或设备声音期间，允许用户在 Controller 选择
一支电脑麦克风，并把处理后的语音回传给指定远端设备：

`电脑麦克风 → Controller 代理麦克风处理链 → 反向传输 → 远端设备播放`

该能力与现有“远程麦克风 → Windows 虚拟录音设备”方向相反，必须使用独立状态、
独立音量和独立生命周期，不能复用一个启用开关造成方向混淆。

## 用户体验

- 每个已连接设备提供“代理麦克风”开关，默认关闭，不随普通音频连接自动开启。
- 首次开启时选择电脑麦克风；可选择跟随 Windows 默认输入或固定设备。
- 显示来源麦克风、目标设备、发送状态、电平、静音、增益和链路质量。
- 支持将同一麦克风发送给一个或多个已连接设备，但每个目标可独立静音和断开。
- 音频连接结束、目标设备主动断开、录音权限撤销或麦克风热拔插时立即停止反向流，
  不在后台自动恢复采集；用户明确重新连接后才允许恢复。
- 默认不把代理麦克风同时监听到本机主输出，避免回声和啸叫。

## 产品边界

- 第一版目标是在 Android 端通过 `AudioTrack` 播放主控麦克风，适用于监听、对讲、
  教学提示和局域网语音回传。
- 普通 Android 应用无法把另一应用提供的音频直接当作系统麦克风输入。若要求微信、
  游戏或会议应用把代理流识别为 Android 麦克风，需要系统权限、厂商接口、root 或
  虚拟音频驱动，不纳入第一版承诺。
- 不录制或持久化原始 PCM；诊断只保存连接状态、时延、丢包和错误计数。

## 架构与协议工作

1. 协议能力协商
   - 为设备声明反向音频接收能力、支持格式、声道数和最大采样率。
   - 新增明确的流方向、流 ID、开始、停止和错误状态，不改变 Protocol v1 既有字段号
     或 Sender → Controller 字节语义。
   - 无反向能力的旧客户端继续单向工作，不能因为升级 Controller 而失去兼容性。
2. Controller 采集与处理
   - 在 `MicrophoneHubCoordinator` 之外建立独立的 `ProxyMicrophoneCoordinator`，
     复用设备枚举与捕获适配器，但单独拥有采集、目标集合和发送生命周期。
   - 语音默认使用 48 kHz 单声道；提供噪声门、压缩、限幅、增益和可选自动增益。
   - 实时线程不执行 UI、日志 I/O、配置保存或阻塞式网络操作。
3. 三种传输反向通道
   - 无线网络：设计经过身份绑定和重放防护的反向媒体通道，并纳入抖动、丢包、
     时钟漂移和拥塞统计。
   - 蓝牙 RFCOMM 与原生 USB：增加全双工帧调度和流方向标识，防止正反向音频互相
     阻塞；带宽不足时优先保证代理语音连续性。
4. Android 接收与播放
   - 在前台服务中管理反向流、`AudioTrack`、音频焦点、输出路由和设备切换。
   - 提供扬声器、听筒、耳机或系统当前通信输出选择；停止时立即释放 AudioTrack。
5. 回声与安全
   - 当远端播放内容可能重新进入电脑麦克风时，提供 AEC 能力探测和明确风险提示。
   - 连接双方继续使用已固定身份；只有当前可信且用户选中的设备能接收代理麦克风。

## 实施批次

该功能在 R3 展示层治理完成后作为独立功能阶段实施，不插入 R3 的结构重构批次：

1. 冻结双向协议提案与兼容测试向量。
2. 实现 Controller 单目标无线网络反向链路和 Android AudioTrack MVP。
3. 增加多目标、音量/静音、电平、设备切换和异常清理。
4. 增加蓝牙与原生 USB 全双工支持。
5. 加入 AEC/AGC 能力、性能优化、配置迁移和完整人工回归。

## 验收标准

- 普通音频正在发送时，可独立开启和关闭代理麦克风，不中断原音频。
- 关闭开关或断开连接后 300 ms 内停止电脑麦克风采集和远端播放。
- 连续切换麦克风、目标设备及三种传输方式，不出现重复采集、残留会话或自动抢连。
- 单目标稳定网络下连续运行 30 分钟，无持续卡顿、无资源增长、语音时延可观测。
- 多目标之间音量、静音和断开互不影响。
- 老版本客户端与新 Controller 保持现有单向音频功能。

## 当前状态

已进入后续开发计划，尚未修改协议或业务代码。现有 Protocol v1 仍只授权
Sender → Controller 的单向音频流。
