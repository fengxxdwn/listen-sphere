# 阶段 4：传输质量与诊断

> 阶段 4 最初在阶段 3 暂缓期间实施；阶段 3“专业调音处理”现已补齐，见
> `stage3-audio-processing-status.md`。

## 第一批：自适应网络缓冲与声道质量

- Wi-Fi UDP 抖动缓冲由固定 30 ms 改为 30–120 ms 自适应目标。
- 到达间隔波动、乱序和缺片会快速提高目标缓冲，优先降低卡顿。
- 连续稳定约 5 秒后每次只回落 10 ms，避免缓冲目标来回跳变。
- 每个 UDP 音频会话独立记录：完成帧、估算丢包、迟到包、补偿静音帧、
  当前缓冲、目标缓冲、估算抖动及目标升降次数。
- Controller 声道卡片显示当前“网络良好 / 网络波动 / 网络较差”及目标缓冲。
- 播放详情显示全局网络缓冲和估算抖动。
- 诊断快照包含自适应目标和网络抖动，不记录 PCM、密钥或设备身份信息。

## 已确认可复用能力

- Windows 播放缓冲已有过高丢帧、过低计数和时钟漂移估算，漂移修正会实际
  作用于播放队列。
- Android Wi-Fi 与蓝牙重连已有有限次数分级退避。
- Android 能识别 Controller 主动断连并停止自动抢连。

## 第二批：重连退避与 60 秒趋势告警

- Windows Sender 按 Controller 设备 UUID 独立维护自动重连退避。
- 连续失败间隔为 1、2、5、10、20、30 秒，之后保持 30 秒上限。
- 用户显式点击连接会清除该目标等待；连接成功后失败计数归零。
- 一台 Controller 失败不会阻塞其他 Controller 的自动连接。
- 每个 Wi-Fi 声道保存最近 60 秒的补偿帧、估算丢包、处理后削波和抖动样本。
- 鼠标停留在声道卡片上可查看 60 秒汇总，不增加主页面常驻信息密度。
- EQ、声道音量和分组增益处理后的峰值超过 0 dBFS 时计为声道削波。
- 质量首次进入“波动”或“较差”时写入隐私过滤的结构化告警。

## 第三批：蓝牙统一质量诊断

- RFCOMM 会话独立记录编码帧、解码帧、时间戳缺口、队列丢帧、解码失败、
  队列深度和估算到达抖动。
- 64 帧低延迟队列继续优先淘汰最旧帧，但淘汰不再静默，会归属到对应会话。
- PCM16、IMA ADPCM 和 AAC-LC 均显示实际协商编码与单/双声道模式。
- 蓝牙声道复用与 Wi-Fi 相同的质量颜色、60 秒趋势和结构化告警入口。
- 声道悬停详情显示最近 60 秒蓝牙丢帧、时间戳缺口、削波、平均抖动和队列深度。
- 全局播放详情与诊断快照加入蓝牙格式、队列、缺口、丢帧和解码失败统计。
- 新增无需蓝牙硬件的时间戳缺口与抖动算法测试。

### 双蓝牙共存掉帧缓解

- Windows 通过设备总线实例与控制器属性识别蓝牙播放端点，不依赖易变化的设备名称。
- 当声音来源和最终输出均为蓝牙时，仅对蓝牙输出自动启用抗抖播放配置：
  100 ms 预缓冲、100 ms WASAPI 播放周期和 500 ms 缓冲容量。
- 普通有线、USB 和内置声卡继续使用低延迟配置，不受额外延迟影响。
- 页面会提示“双蓝牙抗抖缓冲已启用”；若输入仍为 PCM16 双声道，会建议优先改用
  IMA ADPCM 或 AAC-LC，降低 RFCOMM 对同一蓝牙控制器空口时隙的占用。
- 新增蓝牙端点分类测试，覆盖 BTHENUM、BTHA2DP、USB 和内置声卡标识。
- 该措施能显著提高共享蓝牙适配器时的容错，但无法突破蓝牙控制器、驱动、天线与无线干扰的
  物理容量。若仍掉帧，应依次尝试压缩编码、单声道、独立 USB 蓝牙适配器或非蓝牙输出。

## 第四批：稳定性回归与耐久验收工具

- 新增 30 分钟等效长序列回归：连续处理 180,000 个 10 ms 音频帧，并周期性注入
  双帧丢失，验证抖动缓冲容量和自适应目标始终保持有界。
- 新增 10,000 次无线网络/蓝牙目标切换回归，验证重连退避相互隔离且用户切换后可重置。
- 新增 Controller/Sender 耐久监控脚本，按间隔记录窗口响应、内存、句柄、线程和 CPU，
  提前退出或窗口无响应时返回失败，并输出 CSV/JSON 报告。
- 新增 Android 测试包装脚本；中文仓库路径下自动使用临时英文盘符，结束后自动撤销。
- Android Debug 与 Release 各 11 项单元测试均已在 JDK 17 下通过。
- 完整 Wi-Fi、Windows 热点、蓝牙、双蓝牙及模式切换矩阵已写入人工验收文档。
- 自动化开发验收已完成；真实无线硬件的 30–60 分钟耐久测试仍需人工操作后确认。

## 自动验收

- `dotnet build ListenSphere.sln -c Release --no-restore`
- `dotnet test ListenSphere.sln -c Release --no-build`
- 当前结果：零警告、零错误，74 项 .NET 测试通过；Android Debug/Release 各 11 项通过。

## 第一批人工验收

1. 通过 Wi-Fi 连接一个 Sender 并开始播放。
2. 确认声道状态出现“网络良好 · 缓冲 30 ms”附近的提示。
3. 临时制造网络负载或远离接入点，确认缓冲可升高且页面不闪退。
4. 网络恢复稳定后继续运行至少 10 秒，确认缓冲逐步下降而非瞬间跳回。
5. 点击“聆界正在汇聚”查看播放详情，确认可见网络缓冲和抖动数值。
6. 导出诊断包，确认运行快照包含目标缓冲与抖动但不包含音频内容。
